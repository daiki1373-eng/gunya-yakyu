# 段階2入口 統合メモ

## 成果物

- `index.html`：`phase1-shell.html` の13画面シェルへ `legacy-game.html` のプレー要素を統合した単一HTML。
- 参照元の `phase1-shell.html` と `legacy-game.html` は変更していない。

## 接続した箇所

### MatchEngine

- `MatchEngine.start(MatchConfig)` を唯一のゲーム設定入力とし、結果は `Events.emit('match:*')` だけで外へ通知する。
- キャンバス上にナイター球場、投手、打者、野手、投球・スイング・打球の軌道を描画する。
- 球速と球種別の変化、タイミング判定、打球初速・飛距離、オート守備、走者進塁、3アウト交代、3回終了、3回表終了時の後攻リード、サヨナラ、引き分けを実装した。
- ユーザー守備中は球種を選んで投球し、相手打者と守備結果を自動処理する。
- 練習、10球チャレンジ、エキシビションも同じエンジンを使う。非リーグ戦は「このモードを終了」で結果画面へ進める。
- 球種は、まっすぐ・カーブ・スライダー・フォーク・シュート・シンカー・マイ変化球に対応。ショップで解禁済みの球種だけを表示する。
- 投球フォーム、打撃フォーム、マイ変化球の方向・変化量、腕の振り、リリース、スイング速度を試合へ反映する。
- 設定の変更確定時は既存の `Ads.onSettingsChanged()` と `Shell.showDemoAd()` を通り、4秒のデモ広告を表示する。実広告SDK・実課金は追加していない。

### モジュール境界

- `MatchEngine` はDOM、`localStorage`、リーグ、育成、財布、ルーターを参照しない。
- DOM側のキャンバス生成・ボタン配線は画面層の `GameSurface` が担当し、描画ポートを `MatchEngine.mount()` に渡す。
- 能力値は `MatchEngine.HOOKS` の `sweetSpot` / `exitVelocity` / `runSpeed` / `fielderRange` / `pitchSpeed` / `pitchScatter` / `pitchBreak` だけで反映する。
- コイン増減は既存の `Economy`（Wallet実装）経由のまま。試合エンジンからは直接増減しない。
- `localStorage` 呼び出しは `Save` 内の4箇所だけ。確認用キーは `gunya.save.v2.dev`（バックアップ等も `.dev` 系）に変更した。

### P0修正

- P0-1：球団番号とシーズンから決まるシードで、CPU野手9人と先発投手1人を毎回再生成する。全員が能力値と `mult` を持ち、CPUデータ自体は保存しない。同じ球団・シーズンでは同じ選手になる。
- P0-2：リーグ結果が第10節なら、結果画面の主ボタンを「次の試合へ」ではなく「シーズン結果へ」にし、`season` 画面へ遷移する。

## 機能スイッチと残した課題

- `CONFIG.FEATURES` の `persistence`、`leagueProgress`、`leagueRewards`、`correction`、`growth`、`daily` はすべて `false` のまま。
- そのため、リーグ日程の実進行、リーグ報酬付与、育成、スカウト排出、ミッション、永続保存は今回の対象外。第10節分岐は実装済みだが、リーグ進行を有効にするまでは通常プレイだけで第10節へ到達しない。
- 確認用保存キーは用意したが、`persistence=false` のため現段階では `localStorage` へ書き込まない。
- ショップの5秒リワード広告（デモ）は元シェルどおり残している。「広告契機は設定変更だけ」という要約仕様との食い違いは、レビューP1の未決事項として次段階で判断が必要。
- 保存スライスに導出可能なリーグ勝敗を含む点、一時停止から試合放棄確認をキャンセルすると直接試合へ戻る点は、今回対象外のレビューP2として残している。
- `phase1-check.js` の完全実行には `jsdom@24` が必要。この作業環境には `jsdom` がなく、既存スクリプト自体は依存解決で停止した。下記の同等観点はNode VMによる自己点検で確認した。

# 段階2本実装

## 変更点

- `CONFIG.FEATURES` の `persistence`、`leagueProgress`、`leagueRewards`、`correction` を有効化した。`growth` と `daily` は無効のままで、スカウト排出・v1移行も実動作させていない。
- 保存先は開発用の `gunya.save.v2.dev` 系だけ。本体保存前に旧本体を `.bak` へ移し、JSON破損またはスキーマ不正の本体は `.broken` へ退避して、検証済み `.bak` を本体へ戻す。`localStorage` の16呼び出しはすべてSave内にある。
- 保存するリーグ情報を `season` と30試合の結果だけにした。節数・順位・勝敗・ゲーム差は結果から毎回再計算し、CPU選手と日程構造は保存しない。選手、財布、設定など各スライスのv2読込も有効化した。
- 新規データはシーズン1・第1節から始まる。6球団のホーム＆ビジター2回総当たりを10節で進め、ユーザー戦確定時に同節のCPU 2試合を自動決着する。途中放棄では結果・記録・報酬を確定しない。
- CPU戦は先に8%で引き分けを判定し、非引き分けは `homeOverall² / (homeOverall² + awayOverall²)` でホーム勝率を決める。シーズン・節・ホーム球団・ビジター球団から固定シードを作るため再現可能。
- 第10節後は結果画面からシーズン終了へ進み、順位報酬をWalletへ `seasonRank:<season>:<rank>` の理由で記録して次シーズンへ移る。CPU能力はシーズンごとに一律＋3、シーズン6の＋15を上限にした。
- リーグ戦コインはヒット・本塁打・勝敗報酬を試合終了時にまとめ、結果画面へ内訳を出す。Wallet台帳は新しい50件だけを保持する。
- 能力倍率 `1 + 0.30 * (v - 50) / 50` はCorrectionの1関数だけに置き、打撃・長打・走塁・守備範囲・球速・制球・変化を `MatchEngine.HOOKS` から適用する。自軍とCPUで同じ経路を通る。
- `match:end` の購読をMatchFlowの1本に集約し、Economy確定→League確定→`Save.commit('matchEnd')`→`match:settled` の順に固定した。試合終了保存は1回だけで、画面遷移は確定後の `match:settled` を受ける。
- 実課金・実広告SDKは追加していない。既存の設定変更4秒広告とショップのデモ広告だけを維持した。

## 自己テスト結果

- JavaScript構文：合格。
- 内蔵自己テスト：24/24合格。段階2として保存往復、破損退避とバックアップ復旧、1シーズン30試合の自動進行、CPU結果の再現性、補正式の値と両軍HOOK適用、CPUの＋3強化と＋15上限、保存事実の形、`match:end` 1回保存、台帳50件上限を追加した。
- 実進行シミュレーション：10節・30試合確定、10試合に対して保存10回、各 `match:end` は保存1回。10勝時の1位報酬1,500コイン＋確定チケット1枚を受け取り、シーズン2・第1節へ移行。別DOMで財布とシーズン2を再読込できた。
- 保存堅牢化：連続保存で直前本体が `.bak` と一致すること、壊した本体が `.broken` に残り、バックアップの財布・リーグ状態へ復旧することを確認した。
- 静的境界：本番キー文字列なし、`localStorage` 16/16箇所がSave内、MatchEngineの禁止参照なし、`match:end` リスナー1本。
- `NODE_PATH=/tmp/jsdom-test/node_modules node phase1-check.js index.html`：62/67合格。既知の打者帯1件は、第1節が自チーム後攻で3回表の表示が相手1番になる実エンジン挙動が正しく、チェッカーのダミー前提「4番」期待が古い。残る4件は段階1固定の期待（リーグ報酬を付与しない、ホームが仮の第4節・4位、仮データ表示、localStorageへ書かない）で、今回有効化した段階2仕様と意図的に反する。JavaScriptエラー、画面、ナビゲーション、モジュール境界、デザインを含む他62件に新規不合格はない。

## 残課題

- 育成・経験値、スカウト実排出、デイリー／ログイン報酬、v1セーブ移行は機能フラグどおり未実装。本番保存キーには触れていない。
- データ書き出し・読み込み・初期化UIは段階4のまま。開発用v2の通常保存・起動時復旧だけを今回有効化した。
- `phase1-check.js` 自体は変更禁止のため、段階2で反転した4つの期待は更新していない。
- ショップの5秒リワード広告（デモ）と「広告契機は設定変更だけ」の差は、前回からの未決事項として残る。

## 手動確認手順

1. 必要ならブラウザーの開発者ツールで `gunya.save.v2.dev`、`.bak`、`.broken` だけを消し、`index.html?debug=1` を開く。ホームがシーズン1・第1節であることを確認する。
2. リーグ戦を終了し、結果画面にヒット・本塁打・勝敗報酬と合計が出て、財布へ同額が増えることを確認する。「次の試合へ」で第2節になり、順位表と日程に同節3試合の結果が出ることを確認する。
3. 別のリーグ戦を開始して一時停止から放棄し、節数、日程、財布が変わらず同じ相手へ再挑戦できることを確認する。
4. 10節目まで進め、結果画面の「シーズン結果へ」から順位報酬を受け取る。シーズン2・第1節へ戻り、相手選手の各能力が前シーズンより3高いことを確認する。
5. リロードして財布、シーズン、消化済み結果、設定が復元されることを確認する。開発者ツールで本体を不正JSONにして再読込し、`.broken` に不正値が残り、`.bak` の状態へ戻ることを確認する。
6. デバッグシートの「自己テスト」で24/24を確認する。設定変更の4秒デモ広告が従来どおり動き、実広告・実課金が発生しないことも確認する。
